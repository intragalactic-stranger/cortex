## 4. Deviations from plan
1. **Quality axis = mean of GSM8K (flexible) and IFEval**, not a broader suite: the only tasks valid for every model
   family (Gemma 4's loglikelihood benchmarks are not).
2. **Cost uses the best measured load level**, not a fitted optimum: levels were coarse.
3. **Demo GIF** not produced; the M6 site serves the interactive version.

## 5. Decisions I made (veto any)

| | Decision | Why |
|---|---|---|
| ⚑ | Cost metric = $ per 1M **SLO-meeting** output tokens (goodput), not raw throughput | Raw throughput rewards overloaded servers that miss the SLO |
| ⚑ | Best run per (engine, model, GPU) across experiments | Experiments sampled different load levels; the latest run is not always the most complete |
| ⚑ | CPU priced at AWS on-demand list price for the M1 box | The box's real cost; labelled as list price |
| | Guide limited to what was measured; a non-coverage section instead of extrapolation | Project rule: only claims the data supports |

## 6. Challenges & surprises
1. **The frontier is short:** two points dominate everything, and for 4B models quality differences are noise.
2. **The L4's problem is latency headroom, not raw speed:** 33 ms/token single-user decode leaves 17 ms below the SLO,
   so the GPU runs out of SLO-meeting capacity at a handful of users.
3. **First frontier draft picked the latest run per config**, which hid SGLang's best L4 point; switched to the best run.

## 7. Explain-back checklist
